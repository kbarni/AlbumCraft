# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**AlbumCraft**: a native Rust/egui photo organizer with a simple non-destructive editor, part of the *Craft* apps suite. See `AGENTS.md` for the rules and `new_features.md` for the plan and status.

This directory is the git repository and the Cargo workspace (see Code layout below). The parent directory holds local research notes and generated tool bookkeeping; they are deliberately not in the repository.

## Using it from an agent

Register the MCP server with an MCP client, e.g. for Claude Code: `claude mcp add albumcraft -- /path/to/albumcraft --mcp`. Works with or without the window open.

## Build / run / test

Run from the repository root:

```
cargo build            # dev profile: opt-level 1 for the workspace crates, 3 for dependencies
cargo run
cargo test             # every crate of the workspace; tests are inline #[cfg(test)] modules next to the code
cargo test -p albumcraft-core   # one crate
cargo test <name>      # single test, e.g. cargo test ini_tests
cargo run -- --screenshot out.png   # renders a frame, saves it, and exits (used for `docs/screenshots/`; on a tiling window manager retry until the window is wide)
```

- `rust-toolchain.toml` selects plain `stable` (plus clippy and rustfmt) on every platform. On a Windows machine without the MSVC linker, run `rustup set default-host x86_64-pc-windows-gnu` once; a local, gitignored `.cargo/config.toml` can hold that machine's GNU linker workarounds (paths to `.tools/`, used only for the `x86_64-pc-windows-gnu` target). The `windows` crate is a `[target.'cfg(windows)'.dependencies]` entry of the core crate, only used under `#[cfg(windows)]` in core's `mail.rs` (printing on Windows is the suite's `craft-print`). `cargo test`: 317 pass, 26 ignored (demos, data converters, network, real-file, real-trash, real-network and speed checks).
- ONNX Runtime (the AI features' networks) is linked statically through the `ort` crate, which downloads a prebuilt library when building (cached in `~/.cache/ort.pyke.io`); it is the `onnx` Cargo feature, on by default: `cargo build --no-default-features` builds without it, and on Windows with the GNU toolchain it is left out by itself (no prebuilt library). The prebuilt Linux library needs glibc 2.38 and GCC 13's libstdc++ (Ubuntu 24.04, Debian 13) to link and to run, so the Linux packages are built with the `onnx-dynamic` feature instead: nothing of ONNX Runtime is linked in, and `runtime` loads Microsoft's own build of `libonnxruntime.so` (glibc 2.28; same version as ort's prebuilt one, pinned in `package.sh`) from beside the program (`.tar.gz`) or `../lib/albumcraft` (`.deb`, AppImage, Flatpak) when the first network is loaded; without the file `available()` is false and Settings says which file is missing. `ORT_DYLIB_PATH=<file> cargo test -p albumcraft-ai --features onnx-dynamic` tests that way of running. The Windows one uses the dynamic C runtime, so the release is built without `+crt-static` and `package.ps1` puts the Visual C++ runtime DLLs beside the exe (the MSI takes every `.dll` there). On macOS, thin LTO drops std's `__isPlatformVersionAtLeast`, which its CoreML code calls: `build.rs` links clang's `libclang_rt.osx.a` (only a release build fails without it); the macOS library is built for 13.4.
- CI: `.github/workflows/ci.yml` calls the suite's shared gate (`storytold/craft-common-actions`, `gate.yml@main`) on Ubuntu, Windows and macOS: `cargo build --locked --all-targets && cargo test --locked`. Keep `Cargo.lock` committed and up to date (the gate fails if the build changes it).
- **Videos** (`video` Cargo feature, on by default) link the FFmpeg libraries of a playback-only build: run `packaging/ffmpeg/build.sh` once (needs a C compiler, make, pkg-config, nasm, meson, ninja; ~1.5 min on 20 cores; FFmpeg 9.0.2 and dav1d 1.5.5, checksum-pinned, LGPL / BSD, no GPL parts) and add the line it prints to the local `.cargo/config.toml` (`[env] PKG_CONFIG_PATH_x86_64_unknown_linux_gnu = { value = ".tools/ffmpeg/linux-x86_64/lib/pkgconfig", relative = true }`): one key per target, so the same file serves every machine. The bindings (`ffmpeg-next` 9.1, bindgen: needs libclang) find them with pkg-config; `packaging/ffmpeg/rpath.rs` (included by both build scripts) gives the program and the test programs an rpath to them (`$ORIGIN`, `$ORIGIN/../lib/albumcraft` and the build folder); the libraries find each other through their own `$ORIGIN`. `cargo build --no-default-features --features onnx` builds without videos (video files are then left out of the library). `build.sh` also builds on Windows (MSYS2 UCRT64 shell; DLLs in `bin/`, import libraries for GNU ld and MSVC in `lib/`) and macOS (untested so far; `--archive` packs a build to hand over, see `packaging/ffmpeg/README.md`). The Windows release (`release.yml`) builds them in MSYS2 (cached by `build.sh`'s hash) and `package.ps1` builds with `FFMPEG_DIR` (from `.tools\ffmpeg\windows-x86_64` or `$env:ALBUMCRAFT_FFMPEG`; `-NoVideo` without videos) and ships the DLLs and their licence texts beside the exe (the MSI takes every `.dll` and `*-COPYING*` there). With the GNU toolchain, `.tools\ffmpeg\windows-x86_64\bin` must be on `PATH` to run the program or the tests. The Linux release builds them on Ubuntu 22.04 (job `ffmpeg-linux`: glibc 2.35 like the program) and `package.sh` puts them (by SONAME, glibc-checked) in `/usr/lib/albumcraft` (deb, AppImage, Flatpak) or beside the program (`.tar.gz`); the macOS release builds them on its runner and puts them (by install name) in `Contents/Frameworks` (`rpath.rs`: `@executable_path/../Frameworks`), removing the build folder's rpath. CI (`setup-command: packaging/ffmpeg/ci-setup.sh`, `command: packaging/ci-gate.sh`) tests videos on Linux only and builds Windows and macOS without the feature. The tests make sample clips with the `ffmpeg` program when it is installed and skip otherwise; `ALBUMCRAFT_VIDEO_DIR=<folder> cargo test -p albumcraft-core real_videos -- --ignored --nocapture` reads every video of a folder.
- Dev profile deliberately sets `debug = false`, `strip = "debuginfo"`: full debug info produced a 450 MB binary that crashed at startup.
- `ALBUMCRAFT_TRACE=1` prints startup trace lines, how long the scan and `set_library` take, frames over 30 ms (results, geo, the view) and thumbnail arrival. `ALBUMCRAFT_PERF_DIR=<photos> cargo test --release -p albumcraft-core perf_ -- --ignored --nocapture` times decoding, thumbnails (whole folder on 6 threads), the thumbnail cache and import (`perf_import` also needs `ALBUMCRAFT_PERF_DEST`, optionally `ALBUMCRAFT_PERF_LIBRARY`); `perf_raw` needs `ALBUMCRAFT_PERF_RAW=1`; `perf_check_embedded_previews` checks the camera previews against full decodes (`perf_tests.rs`). Measured on 12 MP phone JPEGs from a USB disk: thumbnail 3 ms (embedded preview; 108 ms decoding the picture), 1400 px preview 128 ms, 886 thumbnails in 0.8 s. `ALBUMCRAFT_LANG=fr` forces a language and `ALBUMCRAFT_SHOT_SIZE=900x560` the window's size (a tiling window manager ignores it: run in a nested X server, e.g. `Xephyr :7 -screen 1400x900` and `env -u WAYLAND_DISPLAY DISPLAY=:7 …`), `ALBUMCRAFT_FACE_BOXES=1` shows the editor's face boxes at once, `ALBUMCRAFT_THEME=light|dark` forces a theme and `ALBUMCRAFT_SHOT_VIEW=edit|presets|effects|slideshow|viewer|settings|export|movie|gallery|print|compare|props|zoom|tray|map|place|pin|maps|geometry|import|search|mapscope|crop|collage|sheet|rescan|scroll|notices|dialog|recrop|sort|cached|open|trash|analysis|packs|looks|similar|proposals|update|tags|managetags|tagged|history|folderdates|date|dateshift|geotag` picks the view for `--screenshot` (`collage`: 12 pictures in a photo pile, or the style named by `ALBUMCRAFT_SHOT_STYLE=pile|mosaic|centre|grid|film|clothesline|fan|shape|blend`; `sheet`: the contact sheet; `gallery`: the web-gallery dialog with eight pictures, its theme previews and Instant photos chosen; `viewer`: the full-screen viewer started from the third picture in the editor; `export`: the Export view with six pictures (one left out), a text signature, creator and copyright; `settings`: the Settings dialog at the section named by `ALBUMCRAFT_SHOT_SECTION=interface|folders|editing|slideshow|export|maps|storage|ai`; `import`: the import view with the sample pictures as a card, `search`: the search box with a chip and suggestions, `mapscope`: one folder on the map, `scroll`: the library with large pictures, scrolled to the last one, `rescan`: a scan that finds one folder less while the editor is open, printing `rescan check: kept` when the open picture and the selection survive, `crop`: the crop tool with a 3 × 2 box, `geometry`: also shows the alignment grid, `map`: Places with sample locations, `place`/`pin`: Set location, `maps`: the online-maps question, `sort`: highest rating first, printing `sort check: ok`, `cached`: the catalogue cache shown before the first scan and not after it, printing `cache check: ok`, `open`: three pictures selected and one opened, printing `open check: kept` when the editor steps through those three and the selection stays, `trash`: the question before rejected pictures go to the trash, `analysis`: the status bar while the library is analysed (`ALBUMCRAFT_SHOT_PAUSED=1`: paused), `packs`: Settings › AI features with sample packs of networks (`ALBUMCRAFT_SHOT_AI_OFF=1`: with the AI features turned off), `looks`: "sea" typed, with the "Looks like" section under the exact matches, `similar`: the pictures like one (both with a fixed ranking: sample pictures are never analysed), `proposals`: the editor's Tags section with proposed tags (fixed); ## Code layout

A Cargo workspace (edition 2024) of four crates, split so that a planned server (Docker) and browser (WebAssembly) version can share the code:

- `crates/albumcraft-edit` — the edit pipeline only (`imaging`, `develop`, `looks`, `decor`): pictures in memory, no file access, no threads of its own. Builds for `wasm32-unknown-unknown` (`cargo build -p albumcraft-edit --target wasm32-unknown-unknown`); keep it that way.
- `crates/albumcraft-ai` — what every AI feature needs, with no dependency on the other crates: `runtime` (a network file loaded and run with ONNX Runtime; the `ort` types stay inside it; `available()` is false in builds without it), `models` (the packs of networks, from the built-in `models.json`; files are assets of the project's own releases), `download` (resumable, size and SHA-256 checked, `.part` then renamed), `store` (what was found in each picture: one file of fixed-size records per kind and network in `<data dir>/AlbumCraft/analysis/`, added to only, keyed by path, date and size), `search`, `faces` and the `Analyser` trait (`analyse`, and `analyse_full`, which may ask for the full-size picture). `networks/` holds the networks built into the program (YuNet, with its licence, `prepare_faces.py` and `reference_faces.py`). Core re-exports it as `ai`.
- `crates/albumcraft-core` — everything without a window: `analysis`, `library`, `catalogue`, `commands`, `mcp`, `control`, `exifinfo`, `raw`, `geo`, `thumbcache`, `export`, `gallery`, `movie`, `collage`, `msg` (translatable messages), `locale` (date / number / size formats), `online` (services), `print` (layouts, PDF writer), `slides` (settings). Re-exports the edit crate's modules; its `imaging` adds file loading (`load_source`, `oriented_dims`) to the pipeline.
- `albumcraft` (the root package, `src/`) — the egui app. `main.rs` re-exports the core modules (`pub use albumcraft_core::{library, imaging, …}`), so app code keeps writing `crate::library::…`. Its `online.rs`, `print.rs` and `slides.rs` glob-re-export the core module of the same name and add the window's part (tile textures, printers, music).
- `src/backend.rs` — the `Library` interface between `App` and the pictures: load / save the notes, scan folders, read / write the catalogue cache, thumbnail / preview / zoom jobs, picture sizes, EXIF, file GPS and the GPS index, `.picasa.ini`, a picture reader for print and collage, export, web gallery, movie, collage / contact sheet files. Slow answers come back as `library::Done` on `App.rx`. `LocalLibrary` is today's behaviour (folders on this computer, `library.json`, the `Pool`); a remote library can implement the same trait. `App` and the views must not read files themselves.

## Architecture

Single-window eframe/egui app. `main.rs` parses `--screenshot` / `--mcp` and runs `app::App`.

- `updates.rs` — the check for a newer release and the self-update, through the suite's `craft-update` crate (git dependency on `storytold/craft-libs`, pinned by rev; `updates::APP` names the repo `kbarni/AlbumCraft`, the asset stem `albumcraft` and the app id). `App::updates_ui` (each frame, after the dialogs) runs the check at start once (only while `Store.check_updates`, `persist`, and no dialog is open, so it waits for the online-maps question), takes up a check asked for by the ☰ menu's Check for Updates… or Settings › Interface › Check now, draws the prompt (Update and Restart, Download, Later) and the result window. Closing for an update waits for running tasks; `on_exit` starts the helper that installs it (`start_pending_update`), and `main` first lets a helper started that way finish (`updates::finish_update`). Which files a release offers each install: `albumcraft-<version>-<os>-<arch>.<kind>` with craft-update's tokens (`linux-x86_64` for `.AppImage` / `.tar.gz` / `.deb` / `.flatpak`; `windows-x64` `.msi` / `-portable.zip`; `macos-arm64` `.dmg`; `each_install_finds_its_release_file` checks them). craft-update installs on Windows only files Authenticode-signed by the running copy's publisher (and recognises an MSI install only by the suite's publisher name), and on macOS only an app signed with the suite's Developer ID team: AlbumCraft's unsigned Windows and macOS builds get Download (the release page) instead, as does a copy run from a Cargo build tree. Linux installs update themselves. Its texts are English keys that `MESSAGES` maps to `update-*` messages. `ALBUMCRAFT_SHOT_VIEW=update` shows the prompt for a made-up release; `<APP>_PRETEND_VERSION` (`ALBUMCRAFT_PRETEND_VERSION=0.1.0`) makes a copy believe it is older; `cargo test real_release_check -- --ignored` asks GitHub.
- `display.rs` — on Linux/BSD, asks winit for X11 when `WAYLAND_DISPLAY` points to a socket that does not exist (a variable left over from a Wayland session; winit would otherwise fail with "NoCompositor"). Uses the `winit` crate directly (same version as eframe's).
- `file_dialogs.rs` — file and folder pickers through the suite's `craft-dialogs` (same craft-libs rev as `craft-update`): `App::ask_file(dialog, FileJob)` queues one (a second click while one is open raises it instead), `ui` shows it at the end of the frame with the window as parent (`show_pending(Some(frame))`), `logic` takes the answers first thing (`App::file_answers`) and runs the `FileJob` (export folder and logo, library location, library / left-out folder, collage background and save, import source and destination, gallery folder, movie file, slideshow music, Move to › Other folder); `Unavailable` is reported as an error. The app's `rfd` dependency is only there for its `wayland` feature. Closing goes through `craft-quit`: `craft_quit::on_close_request` is the last line of `App::logic` (after the library has been saved for the close); on macOS it cancels the window close and quits with `-[NSApplication terminate:]` (closing the window can crash in AppKit), elsewhere it does nothing. `on_exit` saves the library and the catalogue cache again when something is left (⌘Q in winit's app menu ends the app without a close request).
- Crash-safe writing: `craft-atomic` (workspace dependency, same rev) for every file AlbumCraft writes: `library::write_library` (library.json, catalogue cache, GPS cache, map tiles, library-location.json), XMP sidecars and embedded XMP (`xmp::write_atomic`; a replaced file keeps its permissions but is a new file: extended attributes and ACLs are not kept), `xmp-none.json`, thumbnails, the analysis tables' `compact`, the vocabulary vectors, collage files, export copies and imports (`write_new`: flushed, then linked under a name that must still be free). Downloads keep their resumable `.part` and are flushed (`sync_file`) before the rename; moves across disks retry the final rename on Windows (`retry_rename`). A crash can leave a hidden `.<name>.<pid>-<n>.craft_tmp` beside the file; the thumbnail cache removes them after an hour.

- `app.rs` — the `App` struct (all UI state: catalogue `Store`, its `lib: Box<dyn Library>`, photos/folders, texture caches, selection (`App::tray`: the selected pictures, or a clicked folder / album / person as a whole), edit state, slideshow, print state, dialogs) and the `eframe::App::update` loop. `View` selects Library / Edit / etc.; `Dialog`, `Tool`, `Tab`, `CompareMode` enumerate modes. Also theme setup and screenshot capture.
- `dialogs.rs` — the dialogs (`App::dialogs`, one `Dialog` at a time, an `egui::Modal`: Esc or a click beside it cancels, Enter presses the main button of the simple ones) and the notices (`App.notices`, stacked over the bottom of the window): `App::toast` (a short note), `App::error` (stays until closed; a failed save is one), `App::undoable` (with an Undo button for 8 s: deleting an album, removing a library folder, the menu's Undo all edits; `Undo` / `App::undo_action`) and the results of background work with Show in folder. **Background work the user waits for is a task**: `App::start_task(label)` gives a `backend::Task` (number + stop switch) passed to `Library::export` / `make_gallery` / `make_movie` / `make_collage`; progress comes back as `Done::Progress`, the end as `Done::Report` (`library::Report`: text, ok or failed, a path to show); the status bar shows each task with a progress bar and Cancel. Stopped work returns `library::STOPPED` from `gallery::write` / `movie::make` and removes what it had made. `demo.rs` — `App::demo_setup`: the fixed sample state behind `--screenshot` and the view picked by `ALBUMCRAFT_SHOT_VIEW`. `slideshow_view.rs` — the full-screen slideshow (`View::Slideshow`) and its control bar. The editor's full-screen button (or F11) starts it as a viewer (`App::start_viewer`): from the current picture, no fade or motion, advancing by itself, music on when a file is chosen; each showing has its own `Slideshow.settings`, and the viewer saves only the interval and music file back to `Store.slideshow`. F11 or Esc leaves. `settings_view.rs` — the Settings dialog (`Dialog::Settings`, ☰ menu or Ctrl+,): the sections listed on the left (Interface, Folders, Editing, Slideshow, Export, Maps, Storage, AI features), the chosen one on the right, in a box of fixed size (inside a modal, separators and scroll areas would otherwise grow without end). Changes apply and are saved at once. It changes the same saved values as the other places that have them (slideshow bar, Export view), plus `Store.bar_style` (the bar at the bottom of the library: compact or tray, see shell.rs), `Store.edit_advanced` (the Edit tab opens on Advanced when the editor is entered), `Store.export_size` / `export_quality` (what the Export view starts with), `Store.export_exif`, `Store.export_creator` / `export_copyright`, `SlideSettings.auto_advance` (off: pictures change only with → or the buttons; the viewer always advances, movies always do) / `captions` / `strong_motion` (pan and zoom 25 % instead of 15 %, also in movies). Cache sizes and emptying go through `Library::cache_sizes` / `clear_cache` (`Done::CacheSizes`; `library::cache_sizes` / `clear_cache`).
- **Left-out folders:** `Store.excluded` (Settings > Folders): folders inside a library folder that scans and the catalogue cache skip with everything under them (`library::scan_roots_except`, `Catalogue::within_except`, `is_excluded`; `Store::add_excluded` / `add_root` check them). Pictures there keep their notes.
- `library.rs` — the catalogue data model (`Store`, `Meta`, `Album`, `Folder`, `Photo`), JSON persistence, `.picasa.ini` import, folder scan, and the background loader `Pool` (worker threads fed by two `Job` queues: urgent first, newest first in both, so what is on screen now comes before what scrolled away; returning `Done` messages over an mpsc channel and calling a `Wake` callback; thumbnails at 256 px (`THUMB_DIM`; 512 px, `SHARP_THUMB_DIM`, for grid tiles larger than that in screen pixels: `App::want_sharp_thumb`, asked for once the usual one is shown, counted four times in `trim_thumbs`), "big" at 1400 px, sharp zoom render up to 5000 px with edits applied).
- `analysis.rs` (core) — the AI features' background work. `Analysis` (owned by `LocalLibrary`) gets the library's pictures after each scan (`Library::analyse`), finds for each `ai::Analyser` the pictures not in its `ai::store::Table` as they are now, and feeds them three at a time to the `Pool` as `Job::Background`: a third queue that runs only while the urgent and normal ones are empty, on at most two workers. Each result is written at once (closing loses nothing; a picture that can't be read is marked and not tried again; an analyser failing 20 times in a row is stopped with a report). Progress is `Done::Analysis` (`App.analysis`, shown in the status bar with Pause / Resume; `Store.analysis_paused`, applied in `App::logic`). The analysers are the search packs' image encoders (`smart_search::use_pack`) and the face analyser (`faces::use_faces`); `look_at` gives `analyse_full` a loader of the full-size picture (at most 4096 px). Also the packs: `packs()` / `download_pack` / `remove_pack` (`Library::model_packs` / `download_pack` (a task) / `remove_pack`; Settings › AI features, `App.packs`). The built-in list (`crates/albumcraft-ai/models.json`) holds the two Smart search packs, Light (OpenCLIP ViT-B/32 LAION-2B, MIT) and Multilingual (SigLIP 2 B/32 at 256 px, Apache 2.0), published on the release `model-1`, and the Faces pack (SFace 2021dec, Apache 2.0, 36.9 MB: `sface-1.onnx`) on the same release.
- `smart_search.rs` (core) — smart search: which search pack is used (none while `Store.ai_enabled` is off, Settings › AI features' first checkbox: then nothing is analysed, searched by look or proposed, and the commands refuse; `chosen`: `Store.search_pack`, else Multilingual, `DEFAULT_PACK`; `active`: the chosen one if downloaded, else any downloaded one; Settings › AI features picks one from a drop-down and downloads it, and offers to remove one no longer chosen), one `Engine` per pack (its `ai::search::Model` and vectors table, loaded once), `search` (typed text or `Query::Like` a picture; all vectors in one int8 matrix per library and table change, a few ms for 50,000 pictures; the text encoder loads at the first text search) and `cut` (how many are shown at first: near the best and, for text, above the pack's `min_score`). If another downloaded pack has vectors for more of the pictures (after a switch, while analysing again), it is used meanwhile. `ai::search` (AI crate) is the network side: `Config` (a pack's `search` section: files, vector size, picture size, mean / std, context, prompt, lower case, punctuation, `min_score`), picture preparation (shorter side to `size`, centre crop), tokens (`tokenizers`), int8 vectors (scale + 512 values). `ALBUMCRAFT_SEARCH_PACK=<dir> cargo test -p albumcraft-ai real_pack -- --ignored` checks an exported pack against its `reference.json`; `XDG_DATA_HOME=<dir with AlbumCraft/models> ALBUMCRAFT_SEARCH_PHOTOS=<folder> cargo test --release -p albumcraft-core real_search -- --ignored --nocapture` analyses and searches real pictures.
- `faces.rs` (core) / `ai::faces` / `faces_view.rs` — faces (phase D of `faces-plan.md` outside the repo; this part: finding and describing the faces). Looked for only while `Store.faces_enabled == Some(true)` and the AI features are on: asked once at a start (`Dialog::Faces`, after the online-maps question, `App::ask_about_faces`; closed without an answer it comes back next start; `ALBUMCRAFT_SHOT_VIEW=faces` shows it) and changed in Settings › AI features ("Find faces and group them by person", with the Faces pack's row); yes downloads the pack (`App::turn_faces_on`). `looks_like.rs`'s 2 s check tells the library (`Library::use_faces(on)`) when that or the pack's presence changes. `ai::faces`: YuNet (OpenCV Zoo 2023mar, MIT, built in: `DETECTOR`, loaded with `Network::load_bytes`; its input size made free by `prepare_faces.py`) looks at the 1400 px picture scaled to 1024 px (`detector_input`: BGR 0…255, padded to 32; `decode`: scores √(cls·obj) ≥ 0.6, boxes, 5 landmarks, NMS 0.3, at most 64 faces); each face is aligned to 112 × 112 on the ArcFace template (`similarity`, `align`: OpenCV's `alignCrop`), cut from the full-size picture when its eyes are under 35 px apart in the preview, and described by SFace (RGB 0…255, 128 values, unit length) when its eyes are 8 px apart or more. `FaceRecord` (208 bytes: box and landmarks as fractions of the unedited, upright picture, score, eye distance, `sharpness` (Laplacian variance of the aligned face), `yaw` (nose along the eye line), from-full flag, int8 vector) in the table `faces.yunet-1-sface-2021dec-1` (with the pack) or `faces.yunet-1` (found only, without it). Face vectors never go to `library.json`, sidecars or copies. Checked against OpenCV's own `FaceDetectorYN` / `FaceRecognizerSF` (`reference_faces.py` then `ALBUMCRAFT_FACES_REFERENCE=… ALBUMCRAFT_FACES_PACK=… cargo test --release -p albumcraft-ai real_faces -- --ignored --nocapture`: 241 faces, boxes to 0.000 px, vectors to a cosine of 1.0000); `ALBUMCRAFT_FACES_PHOTOS=<folder> ALBUMCRAFT_FACES_PACK=<folder> cargo test --release -p albumcraft-core real_faces_analysis -- --ignored --nocapture` times it (73 ms a picture on two threads, about 1 h for 50 000). The int8 SFace of the Zoo is not used (cosine 0.96 to the full one).
- `face_groups.rs` (core) — grouping faces by person (M2), pure logic (merges: `Constraints::resolve`): `regroup(faces, previous, constraints, params)` places only faces in no group (groups are never reshuffled), comparing each with up to 50 exemplars of each group (mean of its 3 best matches ≥ `join`; a quick look at the exemplars' mean first), a face that joined becomes an exemplar only when it matches 2 of them (`support`: groups cannot drift to a look-alike), a new group starts from three good faces that all match each other (`seed`), poor faces (`Params::is_good`: score ≥ 0.85, eyes ≥ 20 px, sharpness ≥ 40, turn ≤ 0.15) only join, a last pass places faces seen before their group existed. **One person is in a picture once**: two faces of one picture never go in one group (a group made before keeps the one that fits best; the user's placements stay); crowds of dark look-alike faces otherwise made groups of strangers with several faces per picture. Not grouped at all (`Params::is_grouped`): detections under 0.8, and faces whose vector is 0.4 or more like the library's non-faces (`nonface_direction`: the mean of its detections under 0.7; hair, wheels, statues, masks, teddy bears otherwise made "people" of their own). `Constraints` (placed faces, "not this person", left-out faces, refused merges, merges; from `faces::decided`). `proposals` (groups that may be one person: the median score of one group's exemplars in the other ≥ `propose`, 0.36; the best of 50 exemplars found a look-alike between any two groups: 409 proposals on the tuning library, 32 with the median, about two thirds of them right by eye), `name_suggestions` (a name typed on most of a group's pictures, `Meta.people`). `faces::group` runs it on the library (`Library::group_faces`, one at a time, again after if asked meanwhile → `Done::Faces(FaceIndex)`: faces per picture, groups largest first with a cover face, proposals; `App.face_groups`, asked by `App::faces_tick` after the first scan, after each scan, every 30 s while analysing, when it ends, and after names or merges change; Settings › AI features shows the counts) and keeps the groups in `<analysis dir>/face-groups.<model>.json` (picture id, place, box, group; a changed picture keeps a face's group when a face is found in the same place). `.picasa.ini` faces (`faces=rect64(…),<contact>`) and `[Contacts]` names are read (`IniFolder.faces` / `contacts`) but not imported yet. On the tuning library (11 347 pictures 2004–2006, 27 456 faces, 1 479 marked by hand for 40 people; `rect64` is in the stored, unturned frame): 97 % of the marked faces found; with the defaults (join 0.45, seed 0.50) pairwise precision 1.000 and recall 0.977, no face in a wrong group, each of the 22 people with 10+ marked faces in one group holding 97–100 % of them, 118 groups of 3+, grouping 25 000 faces in 0.4 s. Join 0.40 puts 16 faces in a wrong group. What the marks can't show and the sheets do: a few groups of strangers at events (dark, turned faces) mix people; the corrections are for those.

- `auto.rs` (edit crate) — the analysis behind the one-click fixes, classical (no network). **Every fix sets sliders, never a step of its own**: `exposure` (exposure, shadows), `contrast` (black point, white point through the exposure, contrast), `lucky` (white balance + both + vibrance) try settings on a sample of the picture with `develop::Curve` and search for the wanted brightness and black / white points; `white_balance` brings the cluster of nearly gray pixels towards gray, part of the way, and leaves a picture without gray parts alone; `geometry` finds straight line segments (`segments`), takes the vanishing point of the upright ones for the straighten angle and the vertical perspective together, or else one long level line (a horizon, at most 5°) for the angle. - `cms.rs` (core) — colour management with the suite's `craft-cms` (pure Rust, same craft-libs rev as `craft-update`). picture menu › Write notes to XMP; Settings › Folders › XMP (`Store.xmp_embedded`).
- `collage.rs` (core) / `collage_view.rs` — collages and contact sheets. Core: `Style` (photo pile, mosaic, centre stage, grid, film strip, clothesline, fan, shape (heart / circle / star), multiple exposure), `collage()` and `contact_sheet()` lay pictures out as `Shape`s on a `Page` in millimetres (pictures as `PhotoShape` cards with frame and shadow, rectangles, lines, text); `render` draws a page into pixels (rotated pictures, soft shadows, gradients, blurred picture backgrounds, text with the UI's font); `save` writes a PDF (`print::pdf_of_pages`, 200 dpi) or one JPEG / PNG per page; `on_paper` fits a page on a printer's paper. Settings in `Store.collage` / `Store.contact_sheet`. The view (`View::Collage`, tray Collage button, menu Contact sheet…) draws the same shapes with the thumbnails as its preview: style tiles drawn from the real layouts, background colour / gradient / picture (a collage picture or any file, via `Job::File`), page size, drag to swap pictures (pile: drag to move, scroll to turn, `Nudge`), Delete leaves the selected one out; Save picture / Save as PDF go through `Library::make_collage`, Print renders on a thread like the print screen. `ALBUMCRAFT_COLLAGE_OUT=<dir> cargo test -p albumcraft-core demo_collages -- --ignored` writes every style and a contact sheet.
- `print.rs` / `print_cups.rs` / `print_view.rs` — print layouts, paper/borders/captions; the pages always go to the printer as a PDF written by core's `print::pdf_of_pages` (JPEG pages placed on the printable area; `print_pages` with `to_file` writes that PDF instead). Windows: the suite's `craft-print` (git dependency on `storytold/craft-libs`, the same rev as `craft-update`): printers from `printer_queues`, paper and printable area from the driver (`rgb::page` with the settings chosen), Printer Setup is the driver's own dialog (`driver_settings_dialog`, kept in `PrinterChoice.settings`), the PDF drawn by Windows.Data.Pdf into the XPS print API (`submit`, `Scaling::Exact`); no `unsafe` of our own. Linux / macOS (`print_cups.rs`, chosen once by `spooler()`): CUPS's programs when installed (see below; only they reach driverless printers that have no queue), else IPP straight to the CUPS socket or `CUPS_SERVER` (`craft-ipp`: `Endpoint::detect`, the printers, the default one; our `ipp` module adds Get-Printer-Attributes (`media-supported`, `media-default`, `printer-resolution-default`) and a Print-Job with `media` and `print-scaling=none`, built with craft-ipp's `Request` and read with its `Reply`, over one HTTP/1.1 exchange of its own), which is what the Flatpak uses (it has `--socket=cups` but not the CUPS programs). CUPS's programs: `craft-print`'s `printers` (`lpstat`, driverless ones too) and `submit` (`lp`, the PDF on stdin, `-o media=`), paper sizes and resolution from `lpoptions -l`. Paper names are IPP's (`iso_a4_210x297mm`) or the PPD's (`A4`); `size_mm` reads both, envelopes and custom ranges are left out of the list, `print::paper_label` shortens IPP names for the screen (`A4`, `Letter`, `4 x 6 in`). 5 mm margins assumed on CUPS. `print::available()` hides every print entry point when no print service answers. Tests never send a job: the IPP ones talk to a fake server on a socket in the temporary folder; `cargo test real_cups -- --ignored --nocapture` lists this machine's printers and paper over IPP; `ALBUMCRAFT_PDF_OUT=out.pdf cargo test print_pdf_demo -- --ignored` writes a sample PDF.

Key design rules:
- **Original files change only when the user asks.** A picture's content is never rewritten (edits are non-destructive), and files are never moved, renamed or deleted on AlbumCraft's own initiative. On the user's request they may be: deleting asks first and uses the system's trash (`library::move_to_trash`), renaming and moving never overwrite and carry the notes along (`files.rs`, `Store::moved`), with Undo. Edits, stars, captions, tags, people, albums are stored as `Meta` in `library.json` under the user data dir (`dirs::data_dir()/AlbumCraft/library.json`, or `albumcraft-library.json` in a folder chosen in Settings › Storage, written in `AlbumCraft/library-location.json`; see `library::store_path`. `relocate_library` (`Library::relocate`) saves it there and removes the old file, never over a library there already, which `open_library_in` opens instead (`Dialog::LibraryThere`, `App::open_library_in` replaces the `Store` and scans again); a chosen folder that can't be reached at start gives `Loaded::Unreadable` with no saving, and Back to the default folder opens the default one. A library saved under the earlier working name `PhotoShelf/` is copied over on first start). Photos are keyed by file path string.
- **`library.json` has a format version** (`Store.version`, `library::FORMAT_VERSION`). A library saved by a newer version is never saved over (`Loaded::Unreadable` with no backup: the window does not save, `--mcp` refuses it), even when this version can't parse it. Settings that a newer version may extend are read with `or_default` (an unknown value becomes the default, not an unreadable library).
- **Dates taken:** `Meta.taken` (core `taken.rs`: a `craft_metadata::DateTime` kept as ISO text, `1978`, `1978-07`, `1978-07-14T10:30:00`; a year or a month alone for scanned prints) overrides the file's date; the file is never changed. The window uses `App::taken_at` (the user's date, else `App.taken`, which stays the file's own so the catalogue cache is right) for sorting, folder dates, the status bar and contact sheets. `date_view.rs`: `date_text` ("1978", "July 1978", a day, a day and time) and the Date taken dialog (`Dialog::DateTaken`, picture menu › Date taken…, or a click on the info panel's date): one date for all, every date moved by as much as the first picture's (`commands::shift_taken`, for a camera clock that was off; pictures without an exact date are left alone), or back to the file's date; each change is an `Undo::Dates` notice. XMP: `XmpNotes.date` (`exif:DateTimeOriginal`, else `photoshop:DateCreated`; not `xmp:CreateDate`, a scan's day; a date equal to the file's EXIF reads as none, `xmp::read_for`), written by Write notes to XMP (a year or month alone in `photoshop:DateCreated` only) and removed there when the user went back to the file's date (`commands::xmp_notes_of`, `date_removed`). Exported and emailed copies get it in their EXIF (`DateTimeOriginal` / `DateTimeDigitized`, a year or month as its first day, the camera's time zone and fractions dropped; `export::set_exif_date`) and, with its precision, in their XMP, even without the notes.
- **Locations:** `Meta.place` (see `geo.rs`); the file's own GPS is read by the background index, never written. Exports carry the location in EXIF when `Store.export_location`. No network unless `Store.online_maps == Some(true)` (only `online.rs` connects, `ai::download` when the user asks for a pack of networks, and the update check, see `updates.rs`).
- **Culling:** `Meta.flag` (`Flag::None/Pick/Reject`) and `Meta.rating` (0–5). Keys P / X / U / 0–5 act on the selection (library) or the current picture (editor); `library_view::flag_rating_menu` / `flag_rating_keys`. The yes/no `star` of older libraries and `.picasa.ini` `star=yes` become picks (`Meta::upgrade`, on load).
- **Copy / paste edits:** `App::copy_edits` / `paste_edits` (Ctrl+Shift+C / Ctrl+Shift+V; plain Ctrl+C/V reach egui as clipboard events, not keys). Pasting puts the copied ops (red-eye fixes excluded, `copyable_edits`) into each picture's own edits with `steps::merge`: a copied adjustment, look, crop or border takes the place of the picture's.
- **`.picasa.ini` files are read once per folder and never written** (tracked via `Store.imported_ini`). The scan thread reads them (`Library::scan`, sent with `Done::Scan`); `App::import_picasa_ini` only merges.
- **A scan keeps the window's state.** `App::set_library` rebuilds `photos` / `folders`, then `keep_across_scan` moves the selection, the open picture, the keyboard's place, print, collage and slideshow pictures to their new ids by file path, and keeps thumbnails and previews of unchanged files (same date and size). Sample pictures are shown only when the library has no folders; folders that can't be reached give an empty library with Scan again / Folders buttons. Notes on sample pictures are never written to `library.json`.
- All decoding/rendering goes through the `Library` (`LocalLibrary` → `Pool`); UI code requests via `Job`s (`App.lib.request`) and consumes `Done` results each frame (textures are cached in `App` maps keyed by photo id).
